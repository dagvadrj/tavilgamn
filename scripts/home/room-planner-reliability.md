# Room planner reliability goal — active

User objective: research IKEA's camera, loading/compression and texture handling; compare it with this planner and implement the improvements needed for a dependable, responsive room planner. This is separate from the completed hybrid homepage hero. Completion is not yet established.

## Completion gates

1. **Evidence and current-state baseline**: reproduce planner entry, populated-room navigation and furniture edits; record production cold/warm load, camera frame intervals/stalls, draw calls, texture/geometry residency, transfer/decode time and console errors. Distinguish historical IKEA bundle evidence from current runtime observations. Do not equate screenshots or SwiftShader timing with physical-device FPS.
2. **Camera and interaction**: smooth orbit/pan/wheel/pinch and focused views, interruption without jumps, stable camera while selecting/replacing furniture, plan/perspective transitions, saved interior viewpoints, reverse/retarget motion, reduced motion, pointer cancellation and touch/drag separation. Run existing camera tests and actual browser interactions before changing established behavior.
3. **GLB delivery and lifetime**: bounded concurrent loads, shared requests, dimensionally correct selectable placeholder, preservation of last valid model, stale completion protection, retries, cancelled/removed furniture cleanup, safe clones and idle memory limits. Pending objects must not leak into exported models or saved previews.
4. **Compression and texture residency**: inspect actual planner assets and the existing offline KTX2/Meshopt/Draco pipeline. Quantify encoded transfer size separately from decoded texture residency. Apply verified derivatives without overwriting catalog originals; preserve UVs, alpha/cutouts, normal precision, material identity, physical bounds, animation and assembly metadata. Validate GPU compressed formats and fallback devices. Do not claim IKEA uses a particular texture-reduction ratio without evidence.
5. **Renderer resilience and frame work**: demand rendering, offscreen/hidden suspension, stable resolution, bounded shadow updates, shader/texture preparation, context-loss recovery that preserves the design, loading/error states and no invisible continuous render loop.
6. **Core planner workflow regression**: room creation/shape/dimensions/openings, multiroom ownership, furniture placement/snapping/collision/attachments, move/rotate/duplicate/delete, undo/redo, materials, catalog filtering, local/save/load reliability, export and preview safety. Keep protected existing UI and user data.
7. **Final verification**: targeted and full tests (classify pre-existing failures with baseline evidence), typecheck, lint/styles, production build and browser runs on desktop plus portrait/landscape touch emulation. Test slow/failed networks and repeated add/remove/switch cycles. Record remaining physical-device limits rather than silently declaring the 30 FPS class of target met.

## Current evidence

- `.tools/rea-ikea-findings.json`: historical US room/add-sofa observation, Draco GLB, measured placeholder and panorama/shading/residual/segmentation/depth imagery. This does not represent every IKEA planner.
- `.tools/ikea-static-mechanics.md`: historical bundle camera target convergence, focus paths, surface-based placement and bounds/contact handling. Exact current runtime application is not verified. The old `.tools/ikea-uk-local-gap-map.md` is a source map to revalidate, not a current list of missing features.
- Current `RoomCanvas` already uses demand rendering and existing camera controllers/motion shadow policy. Current `modelLoader` supports Draco, Meshopt and KTX2. `scripts/models/optimize-glb.mjs` already has resize plus normal-UASTC/other-ETC1S passes. Avoid replacing working infrastructure based on stale assumptions.
- [Three.js GLTFLoader](https://threejs.org/docs/pages/GLTFLoader) documents compressed-loader setup and special ImageBitmap cleanup. Shared `THREE.Cache` is enabled by the legacy OBJ loader, so bitmap closing must respect cross-consumer ownership; indiscriminate `.close()` is unsafe.
- [Three.js KTX2Loader](https://threejs.org/docs/pages/KTX2Loader.html) detects the supported GPU compressed format. [R3F scaling performance](https://r3f.docs.pmnd.rs/advanced/scaling-performance) documents demand rendering and explicit invalidation around camera changes. Runtime implementation must use the installed library versions, not assume latest-doc APIs exist locally.

## Work ledger

- **Implemented: loader residency/cancellation.** Source inspection found an idle-cache limit of four models with no byte limit, queued downloads continuing after all leases are released, and missing disposal if post-decode preparation throws. Added decoded geometry/texture residency estimation, 32 MiB low-memory / 64 MiB default idle allowance, cancellation checks before decode and before preparation, and failure cleanup. Active leases are never evicted. The GLB component now releases pending leases immediately on replacement/unmount; retained displayed models keep their own leases. Late release of a failed lease cannot retire a newer renderer pool. Opt-in canvas diagnostics expose active/idle model bytes and queue size. These estimates exclude environment textures, clone-specific materials, DOM images and process RAM.
- **Current asset audit:** the live Luna delivery (`model-2ac67957-7846-4b0a-a878-8e352d24ddc4.glb`) is already Meshopt + KHR_texture_basisu, 3,455,824 transfer bytes, 297,424 triangles and two 2048-square KTX2 images with 12 mip levels. No additional resolution reduction or catalog overwrite was applied. Existing offline pipeline uses UASTC for normals and ETC1S for other maps; actual delivered slots still need broader asset coverage before any further policy change.
- **Production baseline and after:** `.tools/camera-reliability-baseline-profile.json` and `.tools/camera-reliability-after-profile.json` used headless Chrome with the reported **RTX 4060 / Direct3D11 renderer**, not SwiftShader. Two orbit sequences in each produced no page errors or recorded long tasks. Motion interval p95 was 5.4–5.6 ms before and 5.4 ms after. This is a high-end headless test, not physical-phone display FPS and not evidence of a meaningful camera-speed improvement from the lifetime fix. The after build reported 18,682,880 active model bytes and zero idle/pending models for the single sofa.
